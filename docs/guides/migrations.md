# Migrations & Seeds

`efc db` manages your schema and fixture data on both MongoDB and PostgreSQL.

| Command | Does |
|---|---|
| `efc db generate <name>` | Writes a migration from the difference between your models and your migrations |
| `efc db migrate` | Runs pending migrations in `src/migrations/` as one new batch |
| `efc db rollback [--steps n]` | Reverts the last batch (or `n` batches), newest first |
| `efc db status` | Lists applied (with batch) and pending migrations |
| `efc db seed [name]` | Runs every seed in `src/seeds/`, or just one |
| `efc db sync [--dry-run] [--exit-code]` | Brings the database in line with the models (or reports what would change) |
| `efc db pull` | Writes `defineTable` models for an existing PostgreSQL database |
| `efc db studio [-p 4983]` | Opens a read-only database browser on `127.0.0.1` |

All of them read `DATABASE_URL` from the environment or `.env` (override with `--database-url`); the engine follows the URL scheme.

## Generating a migration from your models

Change a model, then let EFC write the migration:

```bash
efc db generate add_post_views
# → src/migrations/20261023101500_add_post_views.ts
```

`generate` replays your existing migrations into a **throwaway schema** (PostgreSQL) or database (MongoDB) on the same server, compares the result with the models in `src/model(s)/`, and writes the difference. Your development database isn't read or changed, so it doesn't matter that `autoSync` already brought it up to date. Run it without a name to just print the plan.

The file is ordinary code you own and should review:

```ts
// Generated by `efc db generate add_post_views` on 2026-10-23. Review it, then run `efc db migrate`.
import type { MigrationContext } from 'express-file-cluster';

export async function up({ db }: MigrationContext): Promise<void> {
  await run(db, [
    `ALTER TABLE "posts" ADD COLUMN IF NOT EXISTS "views" integer`,
    `CREATE INDEX IF NOT EXISTS "posts_views_idx" ON "posts" ("views")`,
  ]);
}

export async function down({ db }: MigrationContext): Promise<void> {
  await run(db, [
    `DROP INDEX IF EXISTS "posts_views_idx"`,
    `ALTER TABLE "posts" DROP COLUMN IF EXISTS "views"`,
  ]);
}
// …plus a small run() helper: one transaction, checks, and skip-if-applied guards
```

- **PostgreSQL:** the steps are SQL run in one transaction. Tables come first and foreign keys last, so models can reference each other in any order. Every statement is idempotent (`IF NOT EXISTS`, or guarded by a "skip if already applied" query), so running a migration over tables that already exist changes nothing.
- **MongoDB:** the steps create collections, build and drop indexes, and move renamed fields in stored documents.
- **`down()`** is a best-effort reverse. Anything without a safe inverse (a dropped column's data, an added enum value) is listed in a comment.

### What `generate` adds, and what it needs you to ask for

By default a migration contains what `sync` would do: create tables, columns, indexes, enum types and foreign keys, convert changed types, and relax `NOT NULL`s the model no longer asks for. Two kinds of change go further and need a flag:

| You want | Do | The migration |
|---|---|---|
| Rename a field and keep its data | `headline: { type: 'string', renamedFrom: 'title' }` | PostgreSQL: `RENAME COLUMN` (`sync` does this too). MongoDB: `$rename` in the stored documents |
| Drop columns the model no longer declares | `efc db generate <name> --allow-drop` | `DROP COLUMN` (the data is gone; `down()` re-adds an empty column) |
| Enforce `required` and `enum` in the database | `efc db generate <name> --tighten` | `SET NOT NULL` for required fields, `VALIDATE` for enum checks |

Tightening can fail on existing rows, so each step comes with a check that runs first. If anything would fail, the migration stops before changing anything, says how many rows are affected and what to fix, and the next `migrate` retries:

```
GenPost.headline is required, but 3 row(s) of "posts" have no value — fill them in, then run the migration again
```

Foreign keys are validated in the migration the same way, after a count of rows that reference a missing record.

### Checking migrations against the models

```bash
efc db generate --verify
```

`--verify` replays every migration into a throwaway schema and fails (exit code 1) if the result is missing anything the models declare, listing the steps. Use it in CI so a model change can't ship without its migration. With a name, `generate <name> --verify` writes the migration and then verifies it.

### Drift: does the live database match?

```bash
efc db sync --dry-run --exit-code
```

This exits with code 2 when the database differs from the models (and 1 on an error). Run it against staging or production before a deploy.

### Starting migrations on an existing database

An app that has run on `autoSync` already has its tables. To start tracking migrations:

```bash
efc db generate init           # the whole current schema
efc db migrate --baseline      # record it as applied, without running it
```

`--baseline` records every pending migration as applied without running it. Because generated migrations are idempotent, running `init` instead also works: it skips what exists.

## Pulling an existing database (PostgreSQL)

```bash
efc db pull                   # → src/model/<Model>.ts + index.ts
efc db pull --out pulled      # somewhere else, to compare
```

`pull` reads the current schema and writes `defineTable` models. It carries over:

- **Tables and ids:** each table with a single `id` primary key (uuid, integer or bigint) becomes a model. Integer and bigint ids become `id: 'serial'` and `'bigserial'`.
- **Columns and types:** varchar lengths, numeric precision, arrays and native enums. `NOT NULL` becomes `required: true`.
- **Defaults:** `now()`, `gen_random_uuid()`, literals and EFC sequences.
- **Naming:** `naming: 'snake_case'` when the columns follow it, plus `column` overrides and the table name.
- **Indexes:** unique, plain, compound and text indexes.
- **Relations:** foreign keys become `ref`s with `onDelete`. A column like `authorId` becomes an `author` field that keeps the `authorId` column. EFC join tables become many-to-many arrays, and every target model gets back-`relations`.

A schema EFC created pulls back to models that sync finds nothing to change in. For a schema EFC didn't create, anything that has no EFC equivalent is noted at the top of the file: expression or partial indexes, other CHECKs, composite keys, and other defaults. Existing files are kept unless you pass `--force`.

`required` and `default` live in the model, not the database. A table created by `sync` or a migration without `--tighten` has nullable columns and no defaults, so its fields pull back as optional. Generate with `--tighten` if you want `required` enforced (and pulled back).

Coming from Prisma? See [Coming from Prisma](./coming-from-prisma.md).

## Writing a migration by hand

```bash
efc generate migration add_orders
# → src/migrations/20261010120000_add_orders.ts
```

```ts
import type { MigrationContext } from 'express-file-cluster';
import { Order } from '../model/Order.js';

export async function up({ db, engine }: MigrationContext): Promise<void> {
  await Order.sync();
}

export async function down({ db, engine }: MigrationContext): Promise<void> {
  await Order.drop();
}
```

- Files run in **filename order**; the generator's UTC timestamp prefix keeps that chronological.
- `db` is the native client — a mongoose `Connection` or a node-postgres `Pool` — for anything models don't cover (`db.query('ALTER TABLE …')`).
- `Model.sync()` reconciles the table/collection with the model (see [the schema takes care of itself](./database.md#the-schema-takes-care-of-itself)). It never drops a column or data, so it's safe to call from several migrations.
- `Model.drop()` removes the table/collection — for `down()`.

**Do I need migrations at all?** Not for schema shape: tables and indexes are reconciled automatically on first use. Use migrations for what sync deliberately won't do, such as dropping columns, enforcing `NOT NULL`, splitting columns or backfilling data. If you run with `autoSync: false`, you need them for every schema change. `efc db generate` writes most of them for you. Projects created with `create-efc-app` include `src/migrations/00000000000000_init`, which syncs every generated model. Running it is optional. While `generate` replays migrations into its throwaway schema, `Model.sync()` calls inside them do nothing, because they'd mirror today's models and hide every change. So the first `efc db generate` in such an app captures the whole schema, and running it against your existing tables is harmless.

### `efc db sync`

```bash
efc db sync --dry-run   # every model in src/model(s)/: what would change (SQL on PostgreSQL)
efc db sync             # apply
```

Handy as the deploy step when `autoSync` is off. In CI, `--dry-run --exit-code` exits with code 2 when anything would change.

## Batches and rollback

Applied migrations are recorded in `efc_migrations` (a table or collection) with a batch number. Everything one `migrate` run applies shares a batch, and `rollback` undoes exactly that unit:

```
efc db migrate     # applies 0001, 0002 → batch 1
efc db migrate     # applies 0003       → batch 2
efc db rollback    # reverts 0003
efc db rollback    # reverts 0002, then 0001
```

A migration that throws stops the run with exit code 1 and is **not** recorded, so the next `migrate` retries it. Earlier migrations in the same run stay applied — make migrations idempotent where you can (`sync()` already is).

On PostgreSQL, `migrate` and `rollback` take an advisory lock, so several instances running migrations at deploy time serialise instead of racing.

## Seeds

```bash
efc generate seed demo_users
# → src/seeds/demo_users.ts
```

```ts
import { User } from '../model/User.js';

export default async function seed() {
  await User.createMany([{ name: 'Ada', email: 'ada@example.com', password: '…' }]);
}
```

`efc db seed` runs all seeds in filename order; `efc db seed demo_users` runs one. Seeds aren't tracked — they run every time.

## TypeScript and production

The commands run your files in a child process: under `tsx` against `src/` when `tsx` is installed (development), otherwise with plain `node` against the compiled `dist/src/` — production images ship without devDependencies. Force the compiled files with `--dist`.

```dockerfile
# Run migrations as a release step, before starting the new version
CMD ["sh", "-c", "npx efc db migrate --dist && npx efc start prod"]
```

`EFC_DEBUG=1` prints the full stack when a migration or seed fails.

## Studio

`efc db studio` serves a read-only browser at `http://127.0.0.1:4983`: every table/collection with its row count, paginated rows, and expandable JSON cells. It binds to localhost only and rejects anything but `GET`.
